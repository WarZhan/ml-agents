# 01 · 游戏规则与设计思路

## 一、三消游戏规则

Match3（三消）是经典的休闲玩法（如 Candy Crush）：

- 棋盘是一个 `Rows × Columns` 的网格，每格有一个**颜色类型（CellType）**。
- 玩家每步**交换相邻两格**；若交换后某行或某列出现 **3 个及以上同色**连续格子，即"匹配成功"。
- 匹配的格子被**消除**得分，上方格子在重力作用下**下落**，顶部**填充**新的随机格子。
- 消除可能引发**连锁（combo）**：下落填充后又形成新匹配，继续消除，直到棋盘稳定。
- 目标：在有限步数内**最大化累计得分**。

### 特殊类型与计分

除颜色外，每格还有一个**特殊类型（SpecialType）**，用于差异化计分：

| 特殊类型 | 形状（可视化） | 分值字段 | 默认分 | 生成概率 |
| --- | --- | --- | --- | --- |
| 0 普通 | 立方体 Cube | `BasicCellPoints` | 1 | ~70% |
| 1 特殊一 | 球体 Sphere | `SpecialCell1Points` | 2 | ~20% |
| 2 特殊二 | 三轴 Plus | `SpecialCell2Points` | 3 | ~10% |

生成概率见 `Match3Board.GetRandomSpecialType()`：`N=10`，其中 1/10 得类型 2、2/10 得类型 1、其余为 0。

## 二、分层架构（核心设计思想）

Match3 示例最重要的设计思想是 **三层解耦**：把"游戏本身"、"与 ML-Agents 的桥接"、"画面表现"彻底分开。

```
┌──────────────────────────────────────────────────────────────┐
│  表现层（示例工程，纯可视化，不参与决策）                      │
│  Match3Drawer  ·  Match3TileSelector                           │
├──────────────────────────────────────────────────────────────┤
│  游戏逻辑层（示例工程）                                         │
│  Match3Board : AbstractBoard   ← 三消规则、棋盘状态、计分       │
│  Match3Agent : Agent           ← 回合状态机、驱动决策           │
├──────────────────────────────────────────────────────────────┤
│  集成层（ML-Agents SDK, Integrations/Match3）                  │
│  AbstractBoard（抽象接口）· Move（动作编解码）                  │
│  Match3Sensor / Match3SensorComponent（观测）                  │
│  Match3Actuator / Match3ActuatorComponent（动作 + 屏蔽）        │
└──────────────────────────────────────────────────────────────┘
```

### 设计要点

1. **`AbstractBoard` 是唯一的耦合点**。
   ML-Agents 的 Sensor/Actuator 只依赖抽象类 `AbstractBoard`，完全不知道具体游戏怎么实现。
   任何三消类游戏只要继承 `AbstractBoard` 并实现几个方法，就能复用整套 Sensor/Actuator/训练管线。

2. **游戏逻辑不感知 ML-Agents**。
   `Match3Board` 里全是纯粹的三消逻辑（匹配、消除、下落、填充），没有一行"观测/奖励"代码。
   这让游戏逻辑可独立测试、独立复用。

3. **表现层完全旁路**。
   `Match3Drawer` 每帧只是"读棋盘、摆方块"，删掉它训练照常进行。观测走的是 `Match3Sensor`
   直接读棋盘数据，而**不是**去截取画面（即便是视觉观测，也是把棋盘数据编码成图，见文档 03）。

## 三、Agent 的回合状态机

三消是"回合 + 连锁动画"的混合节奏，无法像 3DBall 那样每物理步都决策，因此 `Match3Agent`
用一个**显式状态机**推进流程（源码 `Match3Agent.cs`）：

```
        请求决策(RequestDecision)
                │
                ▼
   ┌────────► FindMatches ──有匹配──► ClearMatched ──► Drop ──► FillEmpty ──┐
   │                │                    (加分)                              │
   │             无匹配                                                       │
   │                ▼                                                         │
   │           WaitForMove ◄──────────────────────────────────────────────┘
   │                │
   │      棋盘无合法move? → 洗牌(InitSettled) 直到有合法move
   │                │
   └──── RequestDecision（请求下一步动作）
```

- **State 枚举**：`FindMatches → ClearMatched → Drop → FillEmpty → WaitForMove`。
- **两种更新节奏**：
  - `FastUpdate()`：**训练 / CI 时**用。一次 `FixedUpdate` 内用 `while` 循环把所有连锁一次性算完，
    立即累加得分、请求下一步决策——不播动画，最快。
  - `AnimatedUpdate()`：**人看时**用。每隔 `MoveTime` 秒推进一个状态，配合 `Match3Drawer` 展示动画。
- **切换依据**：`Academy.Instance.IsCommunicatorOn`（连了训练器）或 `ModelOverrider.HasOverrides`（CI）→ 走 Fast。

```96:116:Project/Assets/ML-Agents/Examples/Match3/Scripts/Match3Agent.cs
        private void FixedUpdate()
        {
            // Make a move every step if we're training, or we're overriding models in CI.
            var useFast = Academy.Instance.IsCommunicatorOn || (m_ModelOverrider != null && m_ModelOverrider.HasOverrides);
            if (useFast)
            {
                FastUpdate();
            }
            else
            {
                AnimatedUpdate();
            }

            // We can't use the normal MaxSteps system to decide when to end an episode,
            // since different agents will make moves at different frequencies (depending on the number of
            // chained moves). So track a number of moves per Agent and manually interrupt the episode.
            if (m_MovesMade >= MaxMoves)
            {
                EpisodeInterrupted();
            }
        }
```

### 为什么不用 MaxStep 结束回合？

因为**不同回合的连锁步数不同**，用引擎步数无法公平界定"下了多少步棋"。所以示例**自己数落子数** `m_MovesMade`，
达到 `MaxMoves`（默认 500）时调用 `EpisodeInterrupted()` 手动截断回合。这是接入非标准节奏游戏的关键技巧。

## 四、奖励设计

奖励极其简单——**得分即奖励**，把三消的"分数"直接乘一个系数作为强化学习奖励：

```118:140:Project/Assets/ML-Agents/Examples/Match3/Scripts/Match3Agent.cs
        void FastUpdate()
        {
            while (true)
            {
                var hasMatched = Board.MarkMatchedCells();
                if (!hasMatched)
                {
                    break;
                }
                var pointsEarned = Board.ClearMatchedCells();
                AddReward(k_RewardMultiplier * pointsEarned);
                Board.DropCells();
                Board.FillFromAbove();
            }

            while (!HasValidMoves())
            {
                // Shuffle the board until we have a valid move.
                Board.InitSettled();
            }
            RequestDecision();
            m_MovesMade++;
        }
```

- `k_RewardMultiplier = 0.01`，即每得 1 分给 0.01 奖励。
- 连锁中每一轮消除都累加，因此策略会**自发学习制造连锁与消除高价值特殊格**。
- 没有步数惩罚——因为总步数由 `MaxMoves` 固定，任务本质是"固定步数内最大化总分"。

## 五、棋盘初始化与"稳定棋盘"

- `InitRandom()`：整盘填随机格子。
- `InitSettled()`：先随机填，再反复"匹配→消除→下落→填充"直到**没有任何现成匹配**为止——
  保证开局不会一上来就自动连锁掉分/送分，让每一步都由智能体决策决定。
- 每步落子后，若当前棋盘**没有任何合法 move**（死局），会反复 `InitSettled()` 洗牌直到有合法解。

这套"保证棋盘始终可玩"的逻辑，是三消 RL 环境能稳定训练的前提。

## 六、小结：本示例演示了什么

| 设计问题 | Match3 的解法 |
| --- | --- |
| 游戏状态不是向量 | 实现 `AbstractBoard`，由 `Match3Sensor` 把棋盘编码成 one-hot 观测 |
| 动作不是移动/连续量 | 把"交换相邻格"编码成离散 `Move` 索引，由 `Match3Actuator` 解码执行 |
| 大量非法动作 | 动作屏蔽：`IsMoveValid` 屏蔽所有不构成三连的交换 |
| 回合节奏不规则 | 显式状态机 + 自数落子数 + `EpisodeInterrupted()` |
| 棋盘尺寸可变 | `GetMaxBoardSize`/`GetCurrentBoardSize` + 观测补零 |
| 训练要快、看要有动画 | `FastUpdate()` / `AnimatedUpdate()` 双节奏切换 |
